# 관리자 역할 관리 설계

## 목적

ZIPUP의 운영 권한을 최고 관리자와 일반 관리자로 분리한다. 최고 관리자는 Supabase 이메일·비밀번호 계정 하나로 운영하며, 소셜 로그인으로 가입한 사용자를 일반 관리자로 추가하거나 해제할 수 있다. 일반 관리자는 기존 관리자 기능을 사용하되 다른 관리자의 권한을 변경할 수 없다.

## 역할

| 역할 | 계정 생성 방식 | 권한 |
| --- | --- | --- |
| `super_admin` | Supabase 이메일·비밀번호 | 관리자 목록 조회, 일반 관리자 추가·해제, 최고 관리자 이전, 기존 관리자 기능 전체 |
| `admin` | Google 또는 Kakao 로그인으로 가입한 사용자 | 문의 처리, GitHub 이슈 전송, 수집·사용자·활동 현황 조회 및 기존 관리자 기능 |
| 일반 사용자 | 모든 일반 로그인 사용자 | 자신의 단지·기록·문의만 관리 |

최고 관리자는 한 명만 존재한다. 일반 관리자는 여러 명일 수 있다.

## 데이터 모델

기존 `public.app_admins`를 역할 테이블로 확장한다.

```text
app_admins
- user_id uuid primary key → auth.users(id)
- role text not null check (role in ('super_admin', 'admin'))
- created_at timestamptz not null
- created_by uuid nullable → auth.users(id)
```

`user_id`는 역할의 식별자이며, 한 사용자는 하나의 관리자 역할만 갖는다. 최초 최고 관리자는 SQL Editor에서 이메일·비밀번호 계정의 UUID를 사용해 `super_admin`으로 등록한다. 이후의 역할 변경은 애플리케이션 API만 사용한다.

현재 `is_support_admin()`은 두 역할 모두 `true`로 처리한다. 새 `is_super_admin()` 함수는 최고 관리자 여부만 반환한다. 두 함수 모두 `security definer`, 제한된 `search_path`, 최소 실행 권한 원칙을 유지한다.

## 관리자 관리 화면

새 경로는 `/admin/admins`다. 기존 `AdminNav`에 **관리자 관리** 항목을 표시하되, 일반 관리자가 접근하면 권한 없음 화면을 표시한다.

화면은 다음 요소로 구성한다.

- 최고 관리자 카드: 닉네임, 가입일, 로그인 제공자, 최고 관리자 이전 버튼
- 일반 관리자 목록: 닉네임, 가입일, 로그인 제공자, 추가일, 추가한 관리자, 해제 버튼
- 사용자 검색: 닉네임 기준 검색 결과에서 소셜 로그인 사용자를 선택해 일반 관리자로 추가
- 감사 기록: 관리자 추가, 해제, 최고 관리자 이전을 시간·실행자·대상·결과와 함께 표시

이메일 주소는 목록과 검색 결과에 표시하거나 저장하지 않는다. 현재 데이터 모델에서 사용자 식별에는 닉네임과 UUID를 사용하며, 이메일은 최고 관리자 계정을 만들 때 Supabase 대시보드에서만 취급한다.

## API와 권한 경계

관리자 관리 API는 서버 전용 Supabase 클라이언트와 service-role 키를 사용한다. 모든 요청은 세션 사용자 확인 후 `is_super_admin()`으로 권한을 재검증한다.

| 경로 | 메서드 | 동작 | 호출 권한 |
| --- | --- | --- | --- |
| `/api/admin/admins` | `GET` | 역할 목록과 검색 결과 조회 | `super_admin` |
| `/api/admin/admins` | `POST` | 소셜 가입자를 `admin`으로 추가 | `super_admin` |
| `/api/admin/admins/[userId]` | `DELETE` | 일반 관리자 해제 | `super_admin` |
| `/api/admin/admins/transfer` | `POST` | 다른 관리자를 최고 관리자로 이전 | `super_admin` |

추가 API는 대상 사용자가 존재하고, 소셜 공급자(`google` 또는 `kakao`)로 가입했으며, 아직 관리자가 아닌지 확인한다. 동일 요청을 반복해도 중복 행이 생기지 않도록 고유 키와 충돌 처리를 사용한다.

## 최고 관리자 이전과 잠금 방지

최고 관리자 이전은 대상이 이미 일반 관리자여야 한다. 전환은 한 트랜잭션에서 수행한다.

1. 대상 관리자가 존재하는지 확인한다.
2. 대상의 역할을 `super_admin`으로 변경한다.
3. 기존 최고 관리자의 역할을 `admin`으로 변경한다.
4. 감사 이벤트를 기록한다.

최고 관리자 행의 삭제와 마지막 최고 관리자 해제는 데이터베이스 함수와 API 양쪽에서 거부한다. 이 제약으로 실수로 관리자 관리 화면에 접근할 계정이 사라지는 상황을 막는다.

## 감사와 오류 처리

기존 `admin_audit_events`에 `admin.grant`, `admin.revoke`, `admin.transfer` 액션을 추가한다. 성공·실패 모두 요청 ID와 함께 서버 로그에 남기며, 사용자 화면에는 다음처럼 일반화된 문구만 표시한다.

- 권한이 없습니다.
- 대상 사용자를 찾을 수 없습니다.
- 이 사용자는 이미 관리자입니다.
- 최고 관리자 이전에 실패했습니다. 잠시 후 다시 시도해 주세요.

UUID, 인증 공급자 내부 오류, 데이터베이스 오류, service-role 관련 정보는 브라우저 응답에 포함하지 않는다.

## 초기 운영 절차

1. Supabase Authentication에서 이메일·비밀번호 최고 관리자 계정을 생성한다.
2. 해당 UUID를 `app_admins`에 `super_admin`으로 등록한다.
3. 최고 관리자 계정으로 `/admin/login`에 로그인한다.
4. `/admin/admins`에서 이미 소셜 로그인한 사용자를 일반 관리자로 추가한다.

## 검증 기준

- 일반 사용자는 관리자 API와 `/admin/admins`에 접근할 수 없다.
- 일반 관리자는 기존 운영 화면을 사용할 수 있지만 관리자 추가·해제·이전을 할 수 없다.
- 최고 관리자는 소셜 가입자를 일반 관리자로 추가하고 해제할 수 있다.
- 최고 관리자 이전 후 새 최고 관리자만 권한 관리 API를 호출할 수 있다.
- 마지막 최고 관리자를 삭제하거나 해제하려는 시도는 실패한다.
- 모든 권한 변경은 감사 이벤트로 남고, HTTP 응답에는 민감한 내부 오류가 포함되지 않는다.
