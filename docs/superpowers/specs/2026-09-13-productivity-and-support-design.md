# 집간격 사용자 편의·문의 기능 설계

**작성일:** 2026-09-13
**상태:** 사용자 승인됨

## 목표

아파트 등록 직후 면적을 자동으로 제시하고, 가격 기록을 쉽게 찾고, 월간·주간 가격 흐름을 전환해 볼 수 있게 한다. 소셜 로그인 이름과 분리된 고유 앱 닉네임을 제공하고, 사용자가 앱에서 보낸 문의가 관리자 GitHub 저장소의 Issue로 바로 접수되게 한다.

## 사용자 경험

### 아파트와 면적

- 사용자는 아파트명을 검색한 뒤 주소가 포함된 후보를 선택한다.
- 후보를 선택하면 별도 버튼 없이 최근 실거래 자료에서 면적을 자동 조회한다.
- 조회 중, 결과 없음, 연결 실패를 면적 입력 영역 안에서 안내한다.
- 면적은 소수점 아래를 버린 정수 단위로 선택한다.
- 카카오 또는 국토교통부 응답의 내부 오류는 서버 로그에만 남기고 사용자에게는 재시도 가능한 일반 메시지를 보여준다.

### 가격 기록 필터

- 실거래가/직접 평가 종류 선택과 함께 단지, 기간, 검색어 필터를 제공한다.
- 검색어는 단지명, 출처, 메모에 적용한다.
- 기간은 전체, 최근 1년, 3년, 5년으로 제공한다.
- 필터는 이미 불러온 사용자 기록에 클라이언트에서 적용한다.

### 주간·월간 차트

- 가격 차트에 월간/주간 전환을 제공한다.
- 월간은 현재와 같이 달력 월의 중앙값을 사용한다.
- 주간은 월요일부터 일요일까지의 중앙값을 사용하며 주 라벨은 시작일을 사용한다.
- 관측이 없는 기간의 가격선은 `connectNulls`로 연결한다.
- 가격 차이는 각 주 또는 월의 가격 변화 시점에 양쪽의 마지막 확인 가격으로 계산한다.
- 주간은 최근 3개월, 6개월, 1년, 3년을 제공하고 월간은 기존 1년, 3년, 5년, 10년을 유지한다.

### 앱 닉네임

- `public.profiles`는 Supabase 사용자마다 하나의 앱 닉네임을 저장한다.
- 첫 로그인 뒤 프로필이 없으면 형용사와 구체적인 동물 종을 조합해 만든다. 소셜 제공자의 이름, 이메일, 사진은 닉네임 생성과 표시에 사용하지 않는다.
- 데이터베이스의 정규화 고유 인덱스가 중복 닉네임을 막는다. 충돌 시 다른 조합을 다시 시도한다.
- 사용자는 설정에서 닉네임을 변경할 수 있다. 앞뒤 공백을 제거하고 2~30자로 제한하며 중복은 명확한 메시지로 거절한다.
- 프로필 생성 실패가 소셜 로그인을 막지 않도록 인증 트리거 대신 로그인 후 인증된 RPC `ensure_profile`을 호출한다.

### 문의 접수

- 로그인한 사용자만 설정의 문의하기 양식을 제출할 수 있다.
- 유형은 오류 제보, 기능 제안, 사용 문의이며 제목과 내용을 필수로 받는다.
- Next.js 서버 경로가 액세스 토큰을 검증하고 서버 전용 `GITHUB_ISSUES_TOKEN`으로 `gnlenfn/real_estate_price_tracker`에 Issue를 만든다.
- GitHub Issue에는 유형, 본문, 현재 화면, 브라우저 정보, 앱 닉네임을 넣는다. 이메일, 소셜 로그인 이름, Supabase UUID는 넣지 않는다.
- 성공하면 이슈 번호를 보여준다. GitHub API의 내부 응답과 토큰 정보는 사용자에게 노출하지 않는다.
- `support_tickets`에 접수 상태와 GitHub 이슈 번호를 저장하고, 최근 1시간에 5건을 넘는 요청을 거부한다.

## 데이터 구조와 보안

`profiles`는 `user_id uuid primary key`, `nickname text`, 생성·수정 시각을 가진다. RLS로 본인 행만 읽고 수정할 수 있으며 닉네임 생성은 인증된 `ensure_profile` RPC가 수행한다. 닉네임 고유 인덱스는 `lower(btrim(nickname))`에 적용한다.

`support_tickets`는 사용자 ID, 유형, 제목, 본문, 화면, 브라우저, 상태, GitHub 이슈 번호와 URL, 생성 시각을 가진다. 사용자는 본인 행만 읽을 수 있다. 생성과 GitHub 결과 갱신은 서버의 Supabase secret key로 수행한다. 새 테이블에는 RLS와 명시적 권한을 함께 설정한다.

브라우저에는 Supabase 공개 키만 전달한다. `GITHUB_ISSUES_TOKEN`과 `SUPABASE_SECRET_KEY`는 서버에서만 읽고 `NEXT_PUBLIC_` 접두사를 사용하지 않는다. GitHub 토큰은 해당 저장소의 Issues 쓰기 권한만 가진 fine-grained token을 사용한다.

## 오류 처리

- 면적 자동 조회는 새 후보를 선택할 때 이전 요청을 취소하고 마지막 선택의 결과만 반영한다.
- 프로필이 없거나 생성 RPC가 일시 실패하면 화면에는 `집 사용자`를 표시하고 다음 새로고침에서 다시 시도한다.
- 닉네임 중복은 다른 이름을 입력하라는 메시지로 변환한다.
- 문의는 먼저 로컬 검증과 시간당 제한을 통과한 뒤 GitHub로 전송한다. GitHub 생성 실패는 실패 상태로 기록하고 사용자가 다시 제출할 수 있게 한다.

## 검증

- 순수 함수 테스트로 주간 집계, 기록 필터, 닉네임 형식·정규화, 문의 검증과 GitHub payload를 확인한다.
- 로컬 Supabase migration을 적용하고 `profiles`, `support_tickets`, RPC, RLS를 확인한다.
- 전체 Node 테스트와 Next.js 프로덕션 빌드를 실행한다.
- 실제 GitHub Issue 생성은 운영 토큰을 설정한 뒤 앱 양식에서 한 건 접수해 확인한다.
