# 문의함 및 운영자 답변 설계

**작성일:** 2026-09-13

## 목표

현재의 단방향 문의 접수를 앱 안에서 답변을 확인할 수 있는 문의함으로 확장한다. 사용자는 별도 `문의` 메뉴에서 문의 작성, 이미지 첨부, 답변 확인을 할 수 있다. 운영자는 일반 사용자 로그인과 분리된 계정으로 전체 문의를 확인하고 답변한다. GitHub Issue는 운영 알림과 업무 추적용 복제본으로 유지하되 사용자 화면에는 GitHub 관련 문구와 번호를 노출하지 않는다.

## 사용자 흐름

사이드바와 모바일 하단 메뉴에 `문의`를 추가한다. 문의 화면은 `문의 작성`과 `내 문의`를 함께 제공한다. 사용자는 유형, 제목, 본문을 입력하고 PNG, JPEG, WebP 이미지를 최대 3개까지 첨부할 수 있다. 이미지 한 개의 최대 크기는 5MB다.

접수 후 사용자는 문의 목록에서 `접수`, `답변 완료`, `종료` 상태를 확인한다. 문의를 열면 최초 내용, 첨부 이미지, 운영자 답변이 시간순으로 표시된다. 사용자는 같은 문의에 추가 메시지와 이미지를 남길 수 있다. 본인 문의만 읽고 쓸 수 있다.

## 운영자 흐름

운영자는 공개 소셜 로그인과 분리된 `/admin/login`에서 이메일과 비밀번호로 로그인한다. 초기 운영자 계정은 Supabase Dashboard에서 이메일 인증 완료 상태로 생성하고 `app_admins`에 등록한다. 일반 사용자의 이메일 로그인과 회원가입 UI는 제공하지 않는다.

`/admin/support`는 전체 문의 목록, 상태 필터, 상세 대화, 첨부 이미지, 답변 입력을 제공한다. 운영자가 답변하면 문의 상태가 `answered`로 바뀐다. 운영자는 문의를 `closed`로 종료하거나 다시 `open`으로 열 수 있다. 관리자 경로를 아는 것만으로는 데이터에 접근할 수 없으며 모든 권한은 데이터베이스 RLS에서 검사한다.

## 데이터 모델

- `app_admins`: 운영자 Auth 사용자 ID와 생성 시각. 본인의 운영자 여부만 조회할 수 있다.
- `support_tickets`: 기존 문의 제목, 유형, 화면, 브라우저, GitHub 연결 정보에 `open`, `answered`, `closed` 상태와 최근 활동 시각을 둔다.
- `support_messages`: 문의별 후속 메시지. 작성자 ID와 작성자 역할을 저장한다.
- `support_attachments`: 문의 및 메시지에 연결된 Storage 경로, 원본 파일명, MIME 형식, 크기를 저장한다.
- 비공개 Storage 버킷 `support-attachments`: `{사용자 ID}/{문의 ID}/{UUID}` 경로를 사용한다.

티켓 소유자는 자신의 티켓, 메시지, 첨부파일만 접근할 수 있다. `app_admins`에 등록된 계정은 모든 문의 데이터에 접근할 수 있다. 첨부파일은 공개 URL을 만들지 않고 인증된 요청에만 짧은 유효기간의 signed URL을 발급한다.

## API와 데이터 흐름

문의 생성 API는 인증, 입력 검증, 시간당 5건 제한을 수행한 뒤 티켓을 저장하고 GitHub Issue를 생성한다. API 응답에는 앱 내부 티켓 ID만 반환한다. GitHub 생성이 실패해도 앱 문의는 유지하고 `github_status=failed`로 기록한다. 사용자는 접수 성공을 확인하며 GitHub 실패는 운영 로그에서 처리한다.

이미지는 티켓이 생성된 뒤 브라우저에서 Supabase Storage로 직접 업로드한다. Storage 정책은 현재 사용자 ID와 해당 티켓 소유자가 일치하는 경로만 허용한다. 업로드가 일부 실패하면 문의는 유지하고 실패한 이미지만 다시 첨부할 수 있게 안내한다. 파일 확장자가 아니라 MIME 형식과 크기를 모두 검증한다.

후속 메시지와 상태 변경은 별도 API를 사용한다. API와 RLS 양쪽에서 티켓 소유자 또는 운영자 권한을 검사한다. 운영자 답변은 GitHub 댓글로 자동 복제하지 않는다. GitHub Issue는 최초 문의의 업무 추적용 복제본으로만 사용한다.

## 화면과 문구

기존 설정 카드의 `GitHub 이슈로 바로 접수`, 성공 메시지의 `GitHub Issue #번호` 문구를 제거한다. 설정 화면의 문의 카드는 제거하고 별도 메뉴로 옮긴다. 사용자에게는 `문의가 접수되었습니다`, `답변이 등록되었습니다`처럼 앱 동작만 설명한다.

관리자 로그인과 문의함은 앱의 일반 내비게이션에 노출하지 않는다. 운영자는 직접 `/admin/login`으로 접근한다. 비관리자 계정이 관리자 경로에 접근하면 세션을 종료하지 않고 일반 앱으로 이동시키며 관리자 데이터는 반환하지 않는다.

## 오류 처리와 보안

- 업로드 가능한 MIME 형식, 파일 수, 파일 크기를 클라이언트와 Storage 정책/서버 검증에서 제한한다.
- Storage 버킷은 항상 비공개로 유지한다.
- GitHub 토큰과 Supabase secret key는 서버에서만 사용한다.
- 관리자 권한은 이메일 문자열이나 사용자 메타데이터가 아니라 `app_admins.user_id`로 판정한다.
- 문의 내용에 포함된 이메일과 UUID는 GitHub 복제본에서 계속 가린다. 앱 내부 문의 원문은 작성자와 운영자만 볼 수 있다.
- 사용자 삭제 시 문의, 메시지, 첨부 메타데이터를 함께 삭제하고 Storage 객체도 정리할 수 있는 서버 작업을 둔다.

## 마이그레이션과 초기 운영자 생성

기존 `support_tickets` 데이터는 유지한다. 새 상태 값과 최근 활동 시각을 채우고 메시지·첨부·관리자 테이블과 Storage 정책을 추가하는 마이그레이션을 만든다. `schema.sql`과 `production-reset.sql`에도 동일한 최신 구조를 반영한다.

운영자는 Supabase Dashboard의 Authentication Users에서 이메일/비밀번호 사용자를 만든 뒤 제공되는 SQL에 그 사용자 UUID를 입력해 `app_admins`에 추가한다. 운영자 비밀번호와 UUID는 저장소에 기록하지 않는다.

## 검증

- 일반 사용자가 본인 문의만 조회하고 다른 사용자의 티켓·메시지·이미지에 접근하지 못하는지 RLS로 검증한다.
- 운영자가 전체 문의 조회, 답변, 상태 변경을 할 수 있는지 검증한다.
- 비관리자 계정이 관리자 API와 화면 데이터에 접근하지 못하는지 검증한다.
- 이미지 수, MIME, 크기 제한과 부분 업로드 실패를 테스트한다.
- GitHub 실패 시에도 앱 문의가 남는지 테스트한다.
- 기존 가격 추적, 소셜 로그인, 단지 자동 실거래 조회의 회귀 테스트와 프로덕션 빌드를 실행한다.
